# Node contract

The Swara language server and the queries in `queries/` depend on the node names below. A rename is a contract change: it updates this file, the queries and the server in the same release.

## The names

- **File and text:** `source_file`, `line_comment`, `block_comment`, `string` (children `escape_sequence`), `number` (which takes a minus sign touching it, as in `-2`, only as the value of an assignment or a property), `number_list` (numbers joined by commas, as in `\time 2,2,3 7/8`), `fraction` (fields `numerator`, `denominator`), `version` (field `value: string`), `include` (field `path: string`), `language` (field `name: string`).
- **Words and commands:** `command` is a leaf for a backslash word, and includes the `\"any text"` form. `identifier` is a word in a position that names something, including a grob or context name after a command inside `\context { }`, `\with { }` or an output definition, as in `\omit TimeSignature`. `dotted_name` is a name with dotted parts, each an `identifier` or a `number`: in music it starts with a `command`, as in `\verse.1`, or with an `identifier` when it is a grob or context path after a command, as in `\omit Staff.TimeSignature`, and before `=` it starts with an `identifier`, as in `verse.1 = …`. `assignment` has fields `name` (`identifier`, `string` or `dotted_name`) and `value`. When the value is flat, such as a number and its unit command, or a command and its arguments, `value` holds each node in order. Only LilyPond's own units, `\mm`, `\cm`, `\in`, `\pt` and `\bp`, join a number's `value`. A variable used as a unit, such as `\staff-space`, is the next expression's `command` instead, because a command on the line after `x = 2` usually starts something new.
- **Blocks:** `header_block`, `paper_block`, `layout_block`, `midi_block`, `context_definition` (`\context { }` inside `\layout` or `\midi`), `score_block`, `book_block`, `bookpart_block`. The three output definitions, `\paper`, `\layout` and `\midi`, hold assignments, Scheme, context definitions, commands and the property commands `override`, `set`, `revert` and `unset`.
- **Contexts and properties:** `new_context` (`\new` or `\context` in music, fields `type: identifier`, optional `name`, optional `with: with_block`, with the music following as the next sibling), `with_block`, `context_modification` (`\consists`, `\remove`, `\accepts`, `\denies`, `\alias`, `\name`, `\type`, `\defaultchild`, `\description` with its argument), `override` and `set` (fields `path: property_path`, `value`), `revert` and `unset` (field `path`), `property_path`.
- **Keyword constructs:** `repeat` (fields `type`, an `identifier` or a `string`, and `count: number`, with the music it repeats following as the next sibling), `alternative` (braces holding the alternatives), `tempo` (an optional field `text`, a `string` or `markup`, then optionally `unit: duration` and `bpm: number`, with a second `bpm` for a range such as `100-120`), `change` (fields `type: identifier` and `name`).
- **Music:** `sequential_music` (`{ }`, and `\sequential { }`), `simultaneous_music` (`<< >>`, and `\simultaneous { }`), `note` (field `pitch: pitch`, whose children are `note_name` and an optional `octave`, followed by an optional `accidental_mark`, an optional `octave_check` and an optional field `duration`), `rest`, `skip`, `multi_measure_rest`, `chord_repetition`, `chord` (`< >` holding notes, with any post-events, commands, Scheme values and grob paths among them, as in `<c \tweak Stem.color #red e>`, then field `duration`), `duration` (a number or `\breve`, `\longa`, `\maxima`, with dots and `*` multipliers). A lone duration in music, as in `c4 8 8`, is a `duration` node in the sequence.
- **Post-events** are siblings of the event they follow, never children, because a command such as `\f` or `\fermata` can itself be a post-event and is parsed flat: `tie`, `slur_start`, `slur_end`, `phrasing_slur_start`, `phrasing_slur_end`, `beam_start`, `beam_end`, `ligature_start`, `ligature_end`, `hairpin` (`\<` and `\>`), `hairpin_end` (`\!`), `articulation` (a direction `-`, `^` or `_` with a shorthand or a command), `fingering`, `string_number`, `tremolo`, `text_script` (a direction with a string or markup), `bar_check`, `voice_separator`. The post-events from `tie` to `hairpin_end` may also begin with a direction, as in `c^(`, and the direction is part of the node.
- **Modes:** `note_mode` (`\notemode` with the music braces or `<< >>` that follow), `drum_mode` (`\drummode`, or `\drums` and an optional `with_block`, with the music braces or `<< >>` that follow), `chord_mode` (`\chordmode`, or `\chords` and an optional `with_block`, with chord braces or chord `<< >>`), `figure_mode` (`\figuremode`, or `\figures` and an optional `with_block`, with figure braces or figure `\simultaneous` braces), `lyric_mode` (`\lyricmode`, or `\lyrics` and an optional `with_block`, with the braces or `<< >>` that follow), `add_lyrics` (`\addlyrics` with lyric braces, lyric `<< >>` or a `command`), `lyrics_to` (an optional field `type: identifier` and `=`, then field `voice`, a `string`, `identifier` or `command`, then lyric braces, lyric `<< >>` or a `command`), `markup`, `markup_list`.
- **Mode content:** `chord_symbol` (fields `root`, optional `duration`, optional `modifiers: chord_modifiers`, optional `inversion`, optional `bass`), `figure_group` (`<`, any `figure`s and `>`, then an optional field `duration`), `figure` (an optional `[`, then a `number`, `_`, `string` or `markup`, then any alterations and `]`), `lyric_word`, `lyric_hyphen` (`--` standing alone), `lyric_extender` (`__` standing alone), `markup_word`, `markup_block`. Inside lyric, chord and figure mode, braces produce `sequential_music` and `<< >>` produce `simultaneous_music`, as they do in music, and an `alternative` holds that mode's braces.
- **Scheme:** `scheme` (the prefix `#` or `$`, then one datum), `scheme_list`, `scheme_vector`, `scheme_quote`, `scheme_quasiquote`, `scheme_unquote`, `scheme_unquote_splicing`, `scheme_symbol`, `scheme_number`, `scheme_string`, `scheme_boolean`, `scheme_character`, `scheme_keyword`, `scheme_comment`, `scheme_block_comment`, `scheme_datum_comment`, `embedded_lilypond`.

## Why commands are flat

A LilyPond command and the expressions after it are siblings in the tree, not parent and children. How many arguments a command takes is known only when LilyPond runs, because any music function can be defined or redefined in the file itself, so a grammar that nested arguments under their command would guess wrong for every function it had not been told about. Parsing flat keeps the tree correct for every function, known or not, and leaves argument counting to the language server, which reads signatures.

These consequences of it are accepted.

- **A note-shaped word is a `note`** even where LilyPond reads it as a word argument, as in `\clef treble`. The server tells the two apart using the command's signature.
- **An assignment whose value does not end in braces, `<< >>`, a block or markup** may absorb a following top-level music expression into its `value`. This changes no colour and raises no error.
- **At the top level, a command's arguments run on past braces**, because a function may take more arguments after a music argument, as in `\fn { c } "x"`. So `\relative c' { c } d` raises no error, although LilyPond rejects the trailing `d`. The server can flag it from the signature.
- **Inside music, `add_lyrics` may follow any sibling**, because the music it attaches to is often a variable, as in `\melody \addlyrics \words`, and a flat tree cannot tell where a function's arguments end. So `{ c \addlyrics { a } }` raises no error, although LilyPond rejects it. At the top level, and at the start of an assignment's value, `\addlyrics` with nothing before it is an error.

## The top level

The top level of a file, and the inside of `\book` and `\bookpart`, holds `version`, `include`, `language`, assignments, blocks and music. That music is either complete in itself (braces, `<< >>`, markup, lyric mode, `\lyricsto`, a Scheme datum or a bar check) or starts with a command, a context, a repeat or an alternative, whose arguments follow as siblings. Verses added with `\addlyrics` may follow either. A note, rest, chord, duration or post-event cannot start top-level music, and a bar check or markup takes no arguments, so `c4 d4` and `| c` at the top level are errors, which is how LilyPond reads them. A string alone at the top level is an unfinished assignment and is an error too. `\score` is the exception: it holds bare music, so `\score { c4 }` is valid where `\book { c4 }` is not.

These words are keywords everywhere: `\override`, `\set`, `\revert`, `\unset`, `\tempo`, `\change`, `\lyricmode`, `\lyrics`, `\addlyrics`, `\lyricsto`, `\chordmode`, `\chords`, `\figuremode`, `\figures`, `\drummode`, `\drums`, `\notemode`, `\markup` and `\markuplist`. Where their construct cannot stand, as `\override` cannot start top-level music, `\lyricmode` cannot follow `\lyricsto`, `\chordmode` cannot take a `\with` block and `\markup` cannot stand inside markup, the word is an error rather than a plain `command`. Inside markup `\override` is a markup command instead, a `command` that takes a Scheme pair, as in `\markup \override #'(font-size . 3) x`. A longer command that begins with one of them, such as `\overrideProperty` or `\setUp`, is still a `command`.

## Lyric mode

Lyric mode changes how words are read and nothing else. A `lyric_word` runs until whitespace, a digit, a backslash, a double quote, a brace, `#` or `$`. Its first character may be any other, apart from `%`, `|`, `*`, `.` and `=`, so `(b`, `'d`, `<a`, `-` and `a.` are each a word. A digit ends a word, so `ab4cd` is a word, a `duration` and a word, and a `%` inside a word is literal, so `ab%cd` is one word. Standing alone, `--` is a `lyric_hyphen`, `__` a `lyric_extender`, and `<<` and `>>` open and close `simultaneous_music`. Touching anything else, each is part of a word, so `a--b`, `a__` and `<<a` are words. An `_` inside a word prints as a space, which is the server's concern rather than the tree's.

Inside `#{ #}` the Scheme reader sees a `%` before LilyPond does, and to the reader it starts a comment, so there a `%` ends a word. A `/` that touches a number before it and a digit after it divides a `fraction`, as in `\time 3/4`. Anywhere else a `/` is a word.

A digit still starts a `duration`, a backslash a `command` and `#` or `$` Scheme, so commands, strings, Scheme, markup, bar checks and the keyword constructs stand in lyric mode as they do in music. `\addlyrics` and `\lyricsto` switch to lyric mode only for the braces or `<< >>` that follow them. A variable after either is a `command`, and `\lyricmode` after either is an error, which is how LilyPond reads them. These rules come from LilyPond 2.26.0, measured on 2026-10-24.

## Chord, figure, drum and note mode

Chord mode reads a `chord_symbol` where music reads a note. Its parts come in a fixed order: a root `pitch`, an optional `duration`, then optionally `:` and `chord_modifiers`, `/` and an `inversion` pitch, and `/+` and a `bass` pitch, as in `c1:m7`, `d:7/fis` and `c/+e`. The modifiers are one token that touches the colon. It holds step numbers, each with an optional `+` or `-` and joined by `.`, words such as `m`, `maj` and `sus`, and `^` before the steps to remove, as in `g:maj7.11+` and `f:9^7`. A space may come before the colon, as in `c4 :m`, but not after it, because LilyPond reads `c: e` as two chords. The tree reads `c:m 7` as a chord and a lone duration. So `c:7.`, `c:+7`, `c:m-`, `c/e:7` and `c:m7/+e/f` are errors, and so is a colon after a chord repeat, a rest or `< >`, which is how LilyPond reads them. Post-events in chord mode take `^` or `_` and never `-`, so `c4-.` is an error, while ties, slurs, phrasing slurs, beams, ligatures and hairpins stand as they do in music. One difference is accepted. `c4^"x"` raises no error, although LilyPond rejects a string above a chord when it runs.

Figure mode reads a `figure_group` where music reads a chord, as in `<6 4>4`. A `figure` is a `number`, `_`, a `string` or `markup`, with an optional `[` before it and any of `+`, `-`, `!`, `\+`, `\!`, `/`, `\\` and `]` after it, as in `<[6 4]>`, `<7+ 5->` and `<6\\>`. Scheme cannot stand in a group, so `<#6>` is an error. Figure mode has no `<< >>`, so `<<` there is an error, as LilyPond reads it, and `\simultaneous` braces produce `simultaneous_music` instead. Post-events take `^` alone, and tremolos, ties, slurs, phrasing slurs, ligatures and hairpins stand, while beams, `\!`, `\\`, `_` and `-` are errors. Rests, skips, chord repeats and lone durations stand in both modes as they do in music, and so does a string, as an argument to the command before it.

Drum mode and note mode read ordinary music, so a drum name such as `bd` or `sn` is a `note` whose `note_name` is the drum's name. LilyPond rejects an octave or an accidental mark on a drum, as in `bd'4` and `bd!`, and a word that names no drum, as in `foo`. The tree accepts all three and leaves the check to the server, which knows the drum names.

`\chords`, `\figures`, `\drums` and `\lyrics` each create a context, so each may take a `with_block` before its music, as in `\chords \with { } { c }`. `\chordmode`, `\figuremode`, `\drummode`, `\notemode` and `\lyricmode` create none and take none, so `\notemode \with { } { c }` is an error. Every mode word needs braces, `<< >>`, `\sequential` braces or `\simultaneous` braces after it, so `\chordmode c` and `\chordmode \x` are errors, even where `\x` holds music. Modes nest freely. Any of them may stand inside music, inside another mode, as an assignment's value or as a function's argument, as in `\lyricmode { \chordmode { c } }`. These rules come from LilyPond 2.26.0, measured on 2026-10-24.

## Markup

`\markup` is followed by any markup commands and their Scheme arguments, then at most one argument: a `markup_block` in braces, a `markup_word`, a `string` or a `score_block`. The commands are flat, as they are in music, so the markup ends after its first argument. That is right for every command with one markup argument. A command with two, such as `\combine`, leaves its second argument outside the markup unless the markup is braced, and at the top level or in a header that stray argument is an error, although LilyPond accepts it. The argument may be left out after a command, because the command can be a variable holding a whole markup or a command that takes no argument, as `\fermata` does. LilyPond rejects a missing argument, as in `\markup \bold` alone, and the server can flag it from the command's signature.

`\markuplist` takes braces or a Scheme datum, after any commands and their Scheme arguments, and never a word or a string. It stands at the top level, in an assignment's value and as a property's value, as in `\set fretLabels = \markuplist { a b }`, and nowhere in music, which is how LilyPond reads it.

A `markup_word` runs until whitespace, a backslash, a double quote, a brace, `#` or `$`. Its first character may be anything else but `%`, which starts a comment there, so a digit, `|`, `=`, `--`, `<<` and `*` are each a word in markup. A `%` inside a word is literal, as in `50%`, except inside `#{ #}`, where the Scheme reader takes it for a comment, as it does in lyric mode. A no-break space and every other space beyond ASCII are part of the word. A `score_block` inside markup returns to note mode, and where lyric mode surrounds a markup that may still take an argument, as after `\markup \bold`, the next word is the markup's.

Whether a command took an argument is unknown to the tree, so what follows a markup that ends in a command is read by these rules.

- **A word followed by `=` starts an assignment.** That is right when the command takes no argument, as `\fermata` and a variable holding markup do, and wrong when it takes one, as in `\markup \bold foo=3`, where LilyPond reads `foo=3` as the markup's word.
- **`\score` is the markup's argument**, which is wrong after a command that takes none.
- **A markup list that ends in a command**, as `\markuplist \table-of-contents` does, is read both as going on and as ending there, and a reading that meets an error is dropped. So music that could not be markup, such as `\relative { c'2 \tocItem \markup "x" }`, is music after it. Where both readings parse, the list goes on, so `\pageBreak \tocItem` after `\table-of-contents` become part of the list.

These rules come from LilyPond 2.26.0, measured on 2026-10-24.

## Comments

A `%` followed by anything but `{` starts a `line_comment`, which ends before the next carriage return or line feed, so a file with Windows line endings parses the same as one with Unix endings. `%{` starts a `block_comment`, which ends at the first `%}`. Block comments do not nest, so `%{ a %{ b %}` is one comment, and `%%%}` closes one. An unterminated `%{` is not a comment: it shows as an error where it opens, which is where LilyPond reports it. A byte-order mark after the start of a file is whitespace, as LilyPond skips it with a warning. Otherwise whitespace is what LilyPond reads as whitespace: space, tab, line feed, carriage return and form feed. A no-break space, an ideographic space and every other space beyond ASCII are letters to LilyPond, so inside a lyric or markup word each is part of the word, and a vertical tab is an error. The scanner decides this itself rather than asking the C library, whose answer for those spaces changes with the locale an editor runs in.

## Reader rules inside `#{ #}`

LilyPond's `#` and `$` each hand exactly one datum to Scheme. Embedded LilyPond, `#{ … #}`, is itself a Scheme datum, so it opens only where Scheme is reading one: after a second `#`, as in `##{ c #}`, or as an element of a Scheme list, as in `#(list #{ c #})` or `$(list #{ c #})`. Directly after LilyPond's own `#` or `$`, Scheme reads `{` as the start of a symbol, and no file binds such a symbol, so `x = #{ c #}` fails to compile. The tree marks that `{` as an error, and a stray `#}` outside embedded LilyPond is an error for the same reason. These verdicts come from LilyPond 2.26.0's exit status, measured on 2026-10-24.

Inside embedded LilyPond, `#}` closes at its first occurrence that is not part of some other token, even when it touches the note before it, so `##{c#}` holds one note. A `#}` is hidden by a `%` line comment, by a `%{ %}` block comment and by a string, and inside embedded Scheme by a Scheme string or a `;` comment. A comment inside a markup block hides the block's closing brace as well, so `##{ \markup { 50% off } #}` leaves the block open and is an error, which is how LilyPond reports it.

A Scheme symbol runs until whitespace, a parenthesis, a double quote, a `;`, a quote, a backquote or a comma. A `#}` or `}` that touches a symbol therefore belongs to it: `#'x#}` quotes the single symbol `x#}`, and `#red}` is the single symbol `red}`, which leaves the enclosing brace unclosed. Inside Scheme `%` is an ordinary symbol character, so `#(let ((%a 1)) %a)` holds no comment. A `#{` inside Scheme inside embedded LilyPond opens a new level that needs its own `#}`, and the scanner counts the levels. Scheme block comments `#| |#` nest the same way, and an unterminated one is an error where it opens.
