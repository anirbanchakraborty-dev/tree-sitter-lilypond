# Node contract

The Swara language server and the queries in `queries/` depend on the node names below. A rename is a contract change: it updates this file, the queries and the server in the same release. The grammar is being built in stages, so some names below are not produced yet. Each is a promise that a later stage keeps under exactly that name.

## The names

- **File and text:** `source_file`, `line_comment`, `block_comment`, `string` (children `escape_sequence`), `number`, `fraction` (fields `numerator`, `denominator`), `version` (field `value: string`), `include` (field `path: string`), `language` (field `name: string`).
- **Words and commands:** `command` is a leaf for a backslash word, and includes the `\"any text"` form. `identifier` is a word in a position that names something. `dotted_name` is a name with dotted parts, each an `identifier` or a `number`: in music it starts with a `command`, as in `\verse.1`, and before `=` it starts with an `identifier`, as in `verse.1 = …`. `assignment` has fields `name` (`identifier`, `string` or `dotted_name`) and `value`. When the value is flat, such as a number and its unit command, or a command and its arguments, `value` holds each node in order. Only LilyPond's own units, `\mm`, `\cm`, `\in`, `\pt` and `\bp`, join a number's `value`. A variable used as a unit, such as `\staff-space`, is the next expression's `command` instead, because a command on the line after `x = 2` usually starts something new.
- **Blocks:** `header_block`, `paper_block`, `layout_block`, `midi_block`, `context_definition` (`\context { }` inside `\layout` or `\midi`), `score_block`, `book_block`, `bookpart_block`. The three output definitions, `\paper`, `\layout` and `\midi`, hold assignments, Scheme, context definitions, commands and the property commands `override`, `set`, `revert` and `unset`.
- **Contexts and properties:** `new_context` (`\new` or `\context` in music, fields `type: identifier`, optional `name`, optional `with: with_block`, with the music following as the next sibling), `with_block`, `context_modification` (`\consists`, `\remove`, `\accepts`, `\denies`, `\alias`, `\name`, `\type`, `\defaultchild`, `\description` with its argument), `override` and `set` (fields `path: property_path`, `value`), `revert` and `unset` (field `path`), `property_path`.
- **Keyword constructs:** `repeat` (fields `type: identifier`, `count: number`, with the music it repeats following as the next sibling), `alternative` (braces holding the alternatives), `tempo` (an optional field `text`, a `string` or `markup`, then optionally `unit: duration` and `bpm: number`, with a second `bpm` for a range such as `100-120`), `change` (fields `type: identifier` and `name`).
- **Music:** `sequential_music` (`{ }`, and `\sequential { }`), `simultaneous_music` (`<< >>`, and `\simultaneous { }`), `note` (field `pitch: pitch`, whose children are `note_name` and an optional `octave`, followed by an optional `accidental_mark`, an optional `octave_check` and an optional field `duration`), `rest`, `skip`, `multi_measure_rest`, `chord_repetition`, `chord` (`< >` holding notes, field `duration`), `duration` (a number or `\breve`, `\longa`, `\maxima`, with dots and `*` multipliers). A lone duration in music, as in `c4 8 8`, is a `duration` node in the sequence.
- **Post-events** are siblings of the event they follow, never children, because a command such as `\f` or `\fermata` can itself be a post-event and is parsed flat: `tie`, `slur_start`, `slur_end`, `phrasing_slur_start`, `phrasing_slur_end`, `beam_start`, `beam_end`, `ligature_start`, `ligature_end`, `hairpin` (`\<` and `\>`), `hairpin_end` (`\!`), `articulation` (a direction `-`, `^` or `_` with a shorthand or a command), `fingering`, `string_number`, `tremolo`, `text_script` (a direction with a string or markup), `bar_check`, `voice_separator`.
- **Modes:** `note_mode`, `drum_mode`, `chord_mode`, `figure_mode`, `lyric_mode` (`\lyricmode` or `\lyrics` with the braces or `<< >>` that follow), `add_lyrics` (`\addlyrics` with lyric braces, lyric `<< >>` or a `command`), `lyrics_to` (an optional field `type: identifier` and `=`, then field `voice`, a `string`, `identifier` or `command`, then lyric braces, lyric `<< >>` or a `command`), `markup`, `markup_list`.
- **Mode content:** `chord_symbol` (fields `root`, optional `duration`, optional `modifiers: chord_modifiers`, optional `inversion`, optional `bass`), `figure_group`, `figure`, `lyric_word`, `lyric_hyphen` (`--` standing alone), `lyric_extender` (`__` standing alone), `markup_word`, `markup_block`. Inside lyric mode, braces produce `sequential_music` and `<< >>` produce `simultaneous_music`, and an `alternative` holds lyric braces.
- **Scheme:** `scheme` (the prefix `#` or `$`, then one datum), `scheme_list`, `scheme_vector`, `scheme_quote`, `scheme_quasiquote`, `scheme_unquote`, `scheme_unquote_splicing`, `scheme_symbol`, `scheme_number`, `scheme_string`, `scheme_boolean`, `scheme_character`, `scheme_keyword`, `scheme_comment`, `scheme_block_comment`, `scheme_datum_comment`, `embedded_lilypond`.

## Why commands are flat

A LilyPond command and the expressions after it are siblings in the tree, not parent and children. How many arguments a command takes is known only when LilyPond runs, because any music function can be defined or redefined in the file itself, so a grammar that nested arguments under their command would guess wrong for every function it had not been told about. Parsing flat keeps the tree correct for every function, known or not, and leaves argument counting to the language server, which reads signatures.

These consequences of it are accepted.

- **A note-shaped word is a `note`** even where LilyPond reads it as a word argument, as in `\clef treble`. The server tells the two apart using the command's signature.
- **An assignment whose value does not end in braces, `<< >>`, a block or markup** may absorb a following top-level music expression into its `value`. This changes no colour and raises no error.
- **At the top level, a command's arguments run on past braces**, because a function may take more arguments after a music argument, as in `\fn { c } "x"`. So `\relative c' { c } d` raises no error, although LilyPond rejects the trailing `d`. The server can flag it from the signature.
- **Inside music, `add_lyrics` may follow any sibling**, because the music it attaches to is often a variable, as in `\melody \addlyrics \words`, and a flat tree cannot tell where a function's arguments end. So `{ c \addlyrics { a } }` raises no error, although LilyPond rejects it. At the top level, and at the start of an assignment's value, `\addlyrics` with nothing before it is an error.

## The top level

The top level of a file, and the inside of `\book` and `\bookpart`, holds `version`, `include`, `language`, assignments, blocks and music. That music is either complete in itself (braces, `<< >>`, markup, lyric mode, `\lyricsto`, a Scheme datum or a bar check) or starts with a command, a context, a repeat or an alternative, whose arguments follow as siblings. Verses added with `\addlyrics` may follow either. A note, rest, chord, duration or post-event cannot start top-level music, and a bar check or markup takes no arguments, so `c4 d4` and `| c` at the top level are errors, which is how LilyPond reads them. A string alone at the top level is an unfinished assignment and is an error too. `\score` is the exception: it holds bare music, so `\score { c4 }` is valid where `\book { c4 }` is not.

Ten words are keywords everywhere: `\override`, `\set`, `\revert`, `\unset`, `\tempo`, `\change`, `\lyricmode`, `\lyrics`, `\addlyrics` and `\lyricsto`. Where their construct cannot stand, as `\override` cannot start top-level music and `\lyricmode` cannot follow `\lyricsto`, the word is an error rather than a plain `command`. A longer command that begins with one of them, such as `\overrideProperty` or `\setUp`, is still a `command`.

## Lyric mode

Lyric mode changes how words are read and nothing else. A `lyric_word` runs until whitespace, a digit, a backslash, a double quote, a brace, `#` or `$`. Its first character may be any other, apart from `%`, `|`, `*`, `.` and `=`, so `(b`, `'d`, `<a`, `-` and `a.` are each a word. A digit ends a word, so `ab4cd` is a word, a `duration` and a word, and a `%` inside a word is literal, so `ab%cd` is one word. Standing alone, `--` is a `lyric_hyphen`, `__` a `lyric_extender`, and `<<` and `>>` open and close `simultaneous_music`. Touching anything else, each is part of a word, so `a--b`, `a__` and `<<a` are words. An `_` inside a word prints as a space, which is the server's concern rather than the tree's.

Inside `#{ #}` the Scheme reader sees a `%` before LilyPond does, and to the reader it starts a comment, so there a `%` ends a word. A `/` that touches a number before it and a digit after it divides a `fraction`, as in `\time 3/4`. Anywhere else a `/` is a word.

A digit still starts a `duration`, a backslash a `command` and `#` or `$` Scheme, so commands, strings, Scheme, markup, bar checks and the keyword constructs stand in lyric mode as they do in music. `\addlyrics` and `\lyricsto` switch to lyric mode only for the braces or `<< >>` that follow them. A variable after either is a `command`, and `\lyricmode` after either is an error, which is how LilyPond reads them. These rules come from LilyPond 2.26.0, measured on 2026-10-24.

## Comments

A `%` followed by anything but `{` starts a `line_comment`, which ends before the next carriage return or line feed, so a file with Windows line endings parses the same as one with Unix endings. `%{` starts a `block_comment`, which ends at the first `%}`. Block comments do not nest, so `%{ a %{ b %}` is one comment, and `%%%}` closes one. An unterminated `%{` is not a comment: it shows as an error where it opens, which is where LilyPond reports it. A byte-order mark after the start of a file is whitespace, as LilyPond skips it with a warning.

## Reader rules inside `#{ #}`

LilyPond's `#` and `$` each hand exactly one datum to Scheme. Embedded LilyPond, `#{ … #}`, is itself a Scheme datum, so it opens only where Scheme is reading one: after a second `#`, as in `##{ c #}`, or as an element of a Scheme list, as in `#(list #{ c #})` or `$(list #{ c #})`. Directly after LilyPond's own `#` or `$`, Scheme reads `{` as the start of a symbol, and no file binds such a symbol, so `x = #{ c #}` fails to compile. The tree marks that `{` as an error, and a stray `#}` outside embedded LilyPond is an error for the same reason. These verdicts come from LilyPond 2.26.0's exit status, measured on 2026-10-24.

Inside embedded LilyPond, `#}` closes at its first occurrence that is not part of some other token, even when it touches the note before it, so `##{c#}` holds one note. A `#}` is hidden by a `%` line comment, by a `%{ %}` block comment and by a string, and inside embedded Scheme by a Scheme string or a `;` comment. A comment inside a markup block hides the block's closing brace as well, so `##{ \markup { 50% off } #}` leaves the block open and is an error, which is how LilyPond reports it.

A Scheme symbol runs until whitespace, a parenthesis, a double quote, a `;`, a quote, a backquote or a comma. A `#}` or `}` that touches a symbol therefore belongs to it: `#'x#}` quotes the single symbol `x#}`, and `#red}` is the single symbol `red}`, which leaves the enclosing brace unclosed. Inside Scheme `%` is an ordinary symbol character, so `#(let ((%a 1)) %a)` holds no comment. A `#{` inside Scheme inside embedded LilyPond opens a new level that needs its own `#}`, and the scanner counts the levels. Scheme block comments `#| |#` nest the same way, and an unterminated one is an error where it opens.
